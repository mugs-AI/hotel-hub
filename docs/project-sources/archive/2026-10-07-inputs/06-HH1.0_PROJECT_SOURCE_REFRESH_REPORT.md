## 4. Cross-project experience incorporated

### SH2.2 / ServiceHub

- Never store raw N3 bearer tokens in browser storage.
- Do not treat unverified JWT claims or failed N3 role resolution as authority.
- Distinguish 401 from 403 and fail closed.
- A former N3 Owner must lose Owner power; continued access requires an active HotelHub role/allowlist.
- Unmatched/inactive/deleted N3 users are blocked.
- UI hiding is not server authorization.
- Keep timelines/audits but hide accounting mechanics from guest-facing outputs.

### PMS / ProjectHub

- Verify exact project, repository, branch and SHA before every Lovable write.
- Prevent generated Supabase browser-auth and dependency drift.
- Treat migration and generated-type parity as one gate.
- Use DD/MM/YYYY everywhere user-facing.
- Keep Settings/verification/capability controls consolidated and avoid oversized cards or duplicated stories.
- A route/component is not complete until mounted, connected and permissioned.

### BEC

- Use stable N3 tenant + product identity for license/trial records.
- Preserve first-join evidence and prevent repeated trial creation.
- License status is server-authoritative; browser state cannot grant access.
- Marketing consent remains separate from product access.
- License expiry/inactive may block product access/figures but must never silently delete hotel/accounting data.
- Any BEC outage/fallback policy must be explicit before integration.

### Van Sales

- Never use display labels as accounting or stock authority; use immutable N3 IDs.
- Source location/account/document context must be server-derived and tenant-scoped.
- Daily settlement-style flows require exactly-once intent/reconciliation—the same principle applies to HotelHub checkout.
- Do not import Van Sales stock/location workflows into HotelHub merely because both integrate with N3.
